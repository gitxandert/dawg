# dawg — Dispatched Alerts While Gone

Lets a coding agent text you on your phone while you're away from the
terminal, and read your replies.

- `dawg` sends push notifications through the [Bark](https://github.com/Finb/Bark) iOS app.
- `dawgd` serves a reply page on your tailnet over HTTPS. `dawg ask` sends a
  notification that opens it, then waits for your answer.
- The inbox page (also served by `dawgd`) is a messages app for your agents:
  one thread per agent session, with its status (busy, blocked, idle), its
  messages and questions, and a box to send it instructions. You can mute a
  thread's texts and still follow it there, and start new agents in
  [herdr](https://herdr.dev).
- `skill/dawg` is a Claude Code skill that teaches the agent when and how to
  use all of it.

## Install

Requirements: Linux with systemd, Python 3.11+, curl, Tailscale, and the Bark
app on your phone.

```bash
./install.sh                 # links, per-user config, dawgd user service
tailscale serve --bg 8787    # once: expose dawgd to your tailnet over HTTPS
```

`install.sh` is safe to re-run and never overwrites existing config. Pass
`--no-service` to skip the systemd unit.

## Configuration

Everything machine- or user-specific lives in `~/.config/dawg/`, outside the
repo:

| File           | Contents                                                      |
| -------------- | ------------------------------------------------------------- |
| `key`          | Bark device key (or set `DAWG_KEY`)                           |
| `dawgd.toml`   | `bind`, `port`, `base_url` (your `https://<host>.ts.net` URL), `tap` |
| `actions.toml` | Commands you can trigger from the phone (see `examples/`)     |
| `token`        | Secret for the inbox and actions pages, generated by dawgd    |

## Usage

```bash
dawg "build finished"                                  # one-way message
dawg run -- make test                                  # notify when a command ends
dawg ask --text -w --json "Deploy now?" Yes No         # ask, wait for the reply
dawg ask --text -w --json "What next?"                 # open question, typed reply
dawg ask --text -w --json --questions qs.json          # several questions, one link
```

Threads, for the inbox:

```bash
id=$(dawg thread new -t myproject)                     # once per agent session
dawg -T "$id" "Migrations done"                        # post to the thread, and text it
dawg status -T "$id" busy "writing tests"              # busy | blocked | idle
dawg ask -T "$id" --text -w --json "Ship it?" Yes No   # shows in the thread, blocked until answered
dawg inbox -T "$id"                                    # messages you sent from the inbox
dawg inbox -T "$id" -w                                 # wait for one
```

`DAWG_THREAD` sets the default for `-T`. Texts sent without a thread (plain
`dawg`, `dawg run`) go to a Notifications thread. A thread muted in the inbox
gets no texts; everything still shows up in the inbox.

## Inbox

Open `<base_url>/m/<token>` (the token is in `~/.config/dawg/token`) and
bookmark it, or add it to your home screen. The list shows every agent's
thread with its status, latest message and unread count. In a thread you
can:

- answer its questions inline, the same as from a notification;
- send it a message: it answers an open question if there's exactly one,
  otherwise it queues until the agent runs `dawg inbox`. An agent in herdr
  that's idle and isn't waiting on `dawg inbox -w` gets it typed into its
  terminal, marked as coming from the inbox so it stays in away mode;
- turn its texts off or on, and archive it.

Keep the inbox open in one tab, or add it to your home screen (in Safari or
Brave: Share, then Add to Home Screen), where it opens full screen as its
own app. It updates live. By default, tapping a text does nothing, because Bark opens every
link in a new browser tab. To have texts open the inbox instead, set `tap`
in `dawgd.toml`:

```toml
tap = "questions"   # asks open the inbox at the question; or "all": every text opens its thread
```

Those links carry the thread's own key, not the inbox token, since links
pass through Bark's push server. Opening your bookmark signs that browser
in with a cookie, and from then on links open the full inbox. In a browser
that isn't signed in, a link shows just its thread.

**New agent** starts Claude Code or Codex in a new herdr workspace, in the
directory you pick, with your task. Its thread is set through `DAWG_THREAD`,
and it goes straight into away mode. For those agents the thread also shows
herdr's view of the agent, a **Terminal** to read its screen and press keys
(for permission prompts), and **Close** to end its workspace.

**Mode** shows a Claude or Codex agent's mode as its terminal footer shows
it, and switches it: Auto, Manual, Accept edits or Plan for Claude, Default
or Plan for Codex. dawg presses shift+tab in the agent's terminal until the
mode it picked shows. For Codex, **Permissions…** opens its approval
presets. **New agent** takes a starting mode too, and an agent restarted
by **Settings** or **Clear** comes back in the mode it was in.

When an agent in herdr stops at a numbered menu in its terminal (a plan
waiting for approval, a permission prompt, a startup question), its thread
shows that menu with the terminal's own options, the plan or the screen
above it, and texts you unless the thread is muted. Picking an option
presses its number in the terminal, so an option that changes the mode
("Yes, and use auto mode", Codex's "Yes, implement this plan") changes it
there too. An option that takes a message, such as "Tell Claude what to
change", sends what you type in the box under the options. The thread shows
the agent as blocked until the menu is gone, and dawg doesn't type queued
messages into it meanwhile.

**Clear** starts a Claude or Codex agent in herdr over with an empty
context, as `/clear` would, while it's idle. It exits the agent and starts a
new session in the same pane, with the same thread, model and effort, so
its background commands (a pending `dawg ask` or `dawg inbox -w`) stop too
and can't report into the new conversation. The thread keeps its messages,
with a divider where the context was cleared; open questions close, and
messages still queued for the old conversation aren't delivered to the new
one. The new agent goes straight into away mode and asks what to work on.
Agents in a plain terminal have no Clear, since dawg can't type into their
terminal.

### Models and usage

The inbox groups threads by service: Claude, Codex, a local model provider
such as Ollama, or Other. Each Claude and Codex group shows that account's
5-hour and weekly limits, as % used or % left (toggle it in the group);
local models have no limits to show. Each thread shows its agent's model,
effort and context use, plus session cost for Claude.

- Claude Code reports through its status line: `install.sh` makes
  `dawg statusline` the status line, unless you already have one.
- Codex agents are read from their session logs in `~/.codex/sessions`,
  once they've run a dawg command (that's how dawg knows which Codex is
  whose).

When a limit passes 80% or 95% you get a text, and a note in the
Notifications thread. Set the levels with `usage_alerts = [80, 95]` in
`dawgd.toml`.

For a Claude or Codex agent running in herdr (started from the inbox, or
started in a herdr pane and using its thread), **Settings** changes its
model and effort. dawg restarts it on the same conversation (`claude
--resume` or `codex resume`) with the new settings, so the change applies
to that agent only and doesn't touch your defaults the way `/model` would.
It stops whatever the agent was running in the background, closes its open
questions, and tells it to re-ask. Agents in a plain terminal show their
settings, but dawg can't type into their terminal to change them. **New
agent** also takes a model and effort, and marks the folder trusted
(unless you untick it) so the agent doesn't ask in its terminal. If a new
agent still stops at a startup prompt (an update notice, say), the thread
says so; answer it from **Terminal** and the task goes in once it's ready.

To use the skill, tell the agent you're stepping away, or run `/dawg`. It
texts you its questions until you type in the terminal again. When it finishes
a task, it asks what to do next and suggests next steps.

For one-way updates only, run `/dawg --non-interactive`, or set the default
in a `dawg.toml`. Put it in a workspace's `.claude/`, `.codex/` or `.agents/`
directory for that workspace, or in the same place under `~` for everything:

```toml
mode = "non-interactive"   # or "interactive" (the default)
```

The flag wins over workspace config, and workspace config wins over global.
